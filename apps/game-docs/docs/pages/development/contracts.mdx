# Native contracts

The game lives in `contracts/l3/world-native`. A small set of domain contracts owns storage and rules for persistent
worlds. Games are keyed by `game_id`; creating a game does not deploy another world. Presets are immutable for a game.

## Facts and storage

The fact declarations in `schema/fact-models.mjs` drive generated bindings for Herald and the client store. Give each
fact one owner and include `game_id` first in game-scoped keys. Avoid redundant rows and derived values stored twice.
Configuration tables belong in immutable deployment/game configuration rather than generated rule code.

Persistent mutations emit the native row events. The codec identifies the model, keys and serialized values; Herald
validates these events and folds all changes from one transaction atomically. Ephemeral stories use their event codec
and recover through history. They are not persistent entity rows.

## Commands and authentication

The season domain receives recorded commands. It checks authority and actor authentication before nonce consumption,
verifies the canonical command commitment and dispatches to the owning domain. Internal commands authenticate their
calling peer. Do not expose generic row setters or an arbitrary actor override.

Recorded context governs gameplay time and randomness. Domain code consumes the root assigned to the accepted action; it
does not sample another root on a retry. The node owns ordering and its volatile admission lifecycle, while recorded
effects are protected against duplicate execution.

## Tests and generated artifacts

Use the versions in `contracts/l3/world-native/.tool-versions` for native contracts and the protocol package. The native
suite uses Foundry's supported partition controls through its existing test command:

```sh
cd contracts/l3/world-native
scarb fmt
scarb build
scarb test
bun scripts/generate-schema.mjs --check
```

When a declaration changes, run `scarb run schema` and review the generated ABI, row and command changes together with
their callers. Test expected gameplay values and rejections directly. Every class must stay below 75,366 CASM felts for
headroom under the chain's 81,920-felt limit. Shrink configuration/code duplication first; split by fact ownership only
when necessary.
