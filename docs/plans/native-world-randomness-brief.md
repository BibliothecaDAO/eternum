# Native world randomness

Updated 2026-09-12. Use secure randomness generated by the trusted sequencing service and recorded once per accepted
action. This supersedes the ECVRF implementation requirement. Protocol, recovery and end-to-end latency gates remain
outstanding; this document does not claim the design is unexploitable.

## Decision and trust boundary

The team operates and trusts the sequencing service to admit and order actions and generate randomness honestly. Use the
operating system's cryptographically secure random generator through a maintained library, then persist the resulting
entropy with the accepted action. There is no dedicated randomness secret key, VRF prover, Cairo VRF verifier or
external randomness provider. Normal player and sequencer transaction-signing credentials remain necessary.

This is recorded sequencer randomness, not a VRF. Anyone can reconstruct execution from the published action and
entropy. They cannot cryptographically establish that the operator sampled honestly, did not privately try alternatives,
or offered fair admission and ordering. A compromised sequencer, journal administrator or authorized submitter lies
inside this trust boundary. Replication protects recovery; it does not make a dishonest operator verifiably fair.

The threat model covers malicious players/accounts, concurrent submissions, duplicate requests, partial failures,
restarts, network partitions and loss of the active host. The three acceptance requirements remain **no previews, no
discarding losses, and no rerolls during recovery**. Reproducibility alone does not satisfy them. Review the protocol
and its implementation before value rides on draws; completion of that review is not a testnet blocker.

Continue executing game state changes on every action. Herald retains its confirmed replay, shared pre-confirmed overlay
and authoritative client state flow. Deferring state computation until game end is outside this change. Neither a future
block hash nor a hardware identifier is the entropy source for this protocol. The mines, Bitcoin and village redesign
remains frozen until the native port reaches those domains.

## Acceptance and execution

1. The player signs the complete intent: chain/deployment identity, game, actor, action nonce, arguments, immutable
   rules/config identity and validity limits. Canonical encoding defines one action identity; caller request IDs,
   transaction hashes and transport retries cannot create alternative identities for the same signed action.
2. The active sequencing leader checks admission and fixes the intent's place in execution order. It obtains fresh
   entropy and atomically commits the signed intent, ticket, order, execution context and entropy envelope to the
   replicated journal. Successful commit is the acceptance boundary. Acknowledge acceptance only after that boundary; do
   not execute, expose entropy or publish a result before it.
3. Submit an ordinary transaction through the authorized sequencing account. The native entrypoint authenticates the
   submitter and player intent, checks deployment/game identity, envelope version, order and duplicate consumption, then
   executes through the owning domains using the recorded root. Players cannot submit or replace a root themselves.
4. Gameplay costs, state changes and row events commit atomically. Persist the execution result durably across the
   declared host-failure boundary before publishing through Herald. Complete transaction data carries the entropy and
   context required to reproduce confirmed execution.
5. Retries, block-capacity deferrals, restart recovery and failover resume the same accepted ticket and envelope.
   Preserve the preceding state and execution context as well as the root; do not recompute outcomes using a new
   timestamp, rules revision, predecessor order or action identity.

Entropy may be sampled while preparing a journal transaction, but it must not be observable or used to execute before
that transaction commits. A crash before commit leaves no accepted draw. An ambiguous commit timeout requires a lookup
by action identity in the authoritative journal, not blind regeneration. Once committed, an entropy binding is immutable
and cannot be sampled again. Concurrent duplicates converge on the same binding; different arguments with an already
used actor nonce are rejected.

Serialize all state-changing commands that could affect an accepted action in the relevant execution order, including
non-random actions. Learning an accepted result must not let a later transfer, capture, cancellation or authorization
change overtake it. Specify expiry and authorization-change behavior at the acceptance boundary and test that neither
can retroactively cancel an observed loss. Legal subsequent gameplay remains possible after the earlier action commits.

Admission failures allocate no accepted ticket. Operational execution failures retain the ticket and root for recovery.
A terminal rejection is recorded as consumed under the protocol's declared failure semantics; it does not grant that
intent another draw. Test panics and returned errors through the action wrapper. If a random loss can cause a reverted
transaction that restores the player's opportunity to try the same action for free, the gate fails. The sequencer must
supply sufficient execution bounds; a player-controlled bound or callback cannot become a selective-abort mechanism.

## Entropy and authorization

Sample a full 32-byte root from the initialized OS generator and check errors. Do not fall back to timestamps, process
IDs, host IDs, transaction hashes or a default seed if entropy is unavailable. OS-generated bytes are suitable for
cryptographic use; the implementation must still check the call's result. Source:
[Linux getrandom](https://man7.org/linux/man-pages/man2/getrandom.2.html).

Version the entropy envelope and specify its canonical byte/felt encoding, action binding and conversion into the
existing game derivation before implementation. Keep deterministic cross-language vectors for that encoding and
derivation. OS generation supplies new roots; neither replay nor recovery tries to reproduce the host's generator state.
Identical accepted records must execute identically on different hosts. New actions receive fresh roots from whichever
authorized leader is active.

Pending roots remain internal to the sequencing service until execution is irrevocable from the player's perspective.
Simulation, fee estimation, debug endpoints, logs and subscriber streams must not disclose roots for cancellable or
unaccepted actions. Production entropy is unavailable through these paths. Test roots are confined to the parity harness
and cannot be injected through a production gameplay entrypoint.

Intents use the existing gameplay key, identity server and PlayerRegistry. Resolve the bound gameplay account through
the registry, read its public key through the approved account interface and verify the intent. PlayerRegistry maps
owner/account addresses; it does not store the public key. Authenticate the account implementation so this lookup cannot
become an arbitrary player callback. There is no second action-key scheme; scoped agent grants remain in
[PR #4963](https://github.com/BibliothecaDAO/eternum/pull/4963).

The sequencing account is a logical service authority, not a machine identity. Rotate its credentials through the normal
authorization mechanism without changing pending action identities, order or roots. Restrict the action entrypoint to
that authority and internal domain entrypoints to their authorized callers. On-chain checks reject
duplicate/out-of-order tickets and foreign submitters; the trusted service is responsible for matching submitted entropy
to the journal.

## Host-independent durability and failover

The accepted journal and execution results must survive loss of the active host and its local disk. Use an existing
replicated transactional storage mechanism with a single committed order and explicit leadership fencing. Document the
chosen mechanism, independent host/storage failure domains, acknowledgement policy and recovery procedure before the
integration run. Own its deployment; no external randomness service is introduced. Do not build a new consensus protocol
or call two processes on the same machine independent durability.

Only the active, fenced leader may accept, bind entropy and submit execution. Stale leaders must be prevented from both
committing journal entries and executing transactions after promotion, including already queued transactions. A lease
check in application code alone is insufficient: demonstrate enforcement at storage and submission/execution boundaries.
Any authority epoch used for fencing is distinct from the immutable action identity; promotion must not invalidate an
accepted ticket or assign it a new draw.

Before promotion, recover and verify the complete accepted ordered prefix, bound entropy, execution context, consumed
nonces and known results against chain progress. Resolve submitted-but-unacknowledged transactions without double
execution. Confirmed transaction history reconstructs confirmed state; it cannot recover a pending root that never
reached the chain. Pending records therefore require independent durable replication before acceptance.

A network partition or missing durability acknowledgement pauses new acceptance/publication. Loss or corruption of all
copies of an accepted binding stops the affected execution stream until authoritative records are restored; generating
fresh entropy is forbidden. Availability under every partition is not a claim. Replayed public data must not require the
original host, its PRNG state or a host-local secret. Access to pending records and authority credentials remains a
service-level operational responsibility.

The integration report must demonstrate promotion onto a different machine after the original machine and local disk
become unavailable. A graceful restart or local file backup alone does not pass host independence. Include the cost of
durable replication and fencing in the end-to-end latency measurement.

## Owned patch, dependencies and release

Keep randomness and the accepted-ticket protocol in a separate crate with one integration point in Madara's batcher,
behind a feature flag. Keep journal/envelope handling within that module; avoid scattered hooks through Blockifier,
syscalls or RPC handlers. Both enabled and disabled builds have gates at every Madara pin bump.

Build from `e67432177060197bb0fb03502f2d07d1194764f5` plus our reviewed patch. Record base commit, patch revision,
feature configuration, resolved dependencies, journal/envelope versions and built image digest in the release artifact.
The current documentation does not claim that this build or deployment exists.

Remove the owned ECVRF suite, Rust prover, Cairo verifier, curve-specific primitive vectors and primitive benchmark from
the implementation scope. The completed cloud prototype remains unmerged; do not import it into the native world. The
earlier third-party primitive was also rejected, and its timings are not carried over. Release dependency checks must
exclude `stark-vrf`, `stark_vrf`, `cartridge_vrf`, Cartridge server and Controller packages from the randomness module,
including vendored/forked copies. No dedicated entropy key generation, verification-key epochs or VRF witness rotation
remains in this plan. Ordinary transaction authentication and service credential rotation remain.

Use the existing rules unchanged for parity. Named purpose domains, explicit draw counters and any change to bounded
sampling are a later versioned random-rules change with vectors; do not silently change outcomes while changing the
entropy transport. Evidence for this track comes from the accepted-ticket protocol, cross-language encoding/derivation,
recovery tests and the complete deployed action, not the superseded primitive smoke.

The pinned Madara implementation batches transactions and re-executes saved transactions at restart. Its existing
pre-confirmed persistence saves executed transactions; the accepted journal and host-loss guarantees above are
additional work. Sources:
[batcher](https://github.com/madara-alliance/madara/blob/e67432177060197bb0fb03502f2d07d1194764f5/madara/crates/client/block_production/src/batcher.rs),
[persistence](https://github.com/madara-alliance/madara/blob/e67432177060197bb0fb03502f2d07d1194764f5/madara/crates/client/db/src/lib.rs#L789),
[recovery](https://github.com/madara-alliance/madara/blob/e67432177060197bb0fb03502f2d07d1194764f5/madara/crates/client/block_production/src/lib.rs#L528).

The fsync conversion defect was reported upstream as
[issue #1257](https://github.com/madara-alliance/madara/issues/1257), followed by
[draft PR #1258](https://github.com/madara-alliance/madara/pull/1258), with a dependency-free source-level reproduction.
The one-file fix is commit `a0b1d029cc2cf9433cd5ea8ff99ec85105ad5f9c`; it passes the source-level reproduction,
repository-configured rustfmt and diff checks. Full mc-db and real RocksDB/recovery tests remain unrun. The original
conversion failed; `opts.set_sync(self.fsync)` passed all four WAL/fsync combinations. This tests the conversion against
an instrumented WriteOptions stand-in with the pinned wrapper's documented default, not real database persistence or
power-loss recovery. Our build must carry the fix until upstream merges it and the adopted pin contains it. Track the
fix in the same release artifact; a real RocksDB integration check and recovery drills remain required.

## Predeclared comparison budget

Measure a deployed explore using the accepted-ticket protocol against today's explore. Keep chain pin, hardware, 250 ms
pre-confirmed cadence, action mix, discovery fixtures and offered load identical. Compare embedded placement and a
sidecar submitting through its own account with the same protocol, replication guarantees and ticket-order checks.

Freeze the run manifest, warmup/sample counts and workload before collecting results. The acceptance budget remains at
most **+25 ms p95** and **+50 ms p99** submission-to-pre-confirmed-row latency versus baseline, at least **95%** of
baseline sustained throughput, and no additional failed actions or ticket-order violations. Report p50/p95/p99 for gas,
execution time and row latency. Include admission, OS generation, replicated journal commit, transaction checks,
execution, result persistence and Herald delivery. Do not change the budget after seeing the results.

The design requires no future block or external entropy round trip, but durable replication adds processing and network
cost. Removing the VRF does not establish zero latency impact. Describe results as within budget when that is what the
measurement supports. Choose embedded placement using the measured latency, ordering/recovery behavior and patch
maintenance cost; it remains the preferred direction.

## Integration gates

Demonstrate one complete protected random action through sequencing, Cairo and Herald. This track remains independent of
the native slice's parity run with injected roots.

- Authenticate signed intents and the sequencing submitter; reject foreign games/deployments, altered arguments, forged
  actors, player-supplied roots, malformed/version-mismatched envelopes and direct internal-domain calls.
- Race duplicate submissions and conflicting actor nonces; exactly one accepted record and at most one gameplay effect
  survive. Retry and block-capacity deferral preserve the action identity, order, root and execution context.
- Attempt previews through simulations, estimation, zero fee bounds, direct entropy requests, logs and subscriptions.
  Public exposure cannot precede irrevocable acceptance; later state changes cannot overtake the accepted action.
- Attempt malicious account validation, losing-result reverts, callbacks, extra multicalls, insufficient execution
  bounds, expiry, cancellation and authorization changes. Test panics and returned errors: neither grants a fresh draw
  or permits a player to discard an accepted loss.
- Crash before/after entropy sampling, replicated commit, acceptance acknowledgement, submission, execution, result
  persistence and publication. Include lost acknowledgements and ambiguous commits. Recover committed records unchanged;
  uncommitted proposals must never have been executed or exposed.
- Remove the active host and its local disk, promote a replica on another host, and resume the accepted ordered prefix.
  Test stale-leader submissions, partitions, VM/container restore, corrupted/missing journal entries and loss of all
  authoritative copies. Resume only with the original binding, or stop; never reseed accepted work.
- Rotate service signing credentials while actions are pending; restore the same accepted actions without any dedicated
  randomness key. Test entropy-source failure and ensure there is no predictable fallback.
- Reconstruct confirmed state on a different host from chain history alone, then compare with the live Herald fold.
  Pending recovery uses the replicated journal. Reconnect and pre-confirmed resets preserve existing Herald semantics.
- Disable external randomness-provider access while retaining required chain/storage connectivity; the complete action
  still works. Verify dependency exclusions and both batcher feature configurations.
- Compare embedded and sidecar execution under competing traffic, with fencing and the same durability policy. Record
  the predeclared gas, execution time, event volume, throughput and row-latency distributions.

## Relationship to the native slice and later lottery

[Native spike commit 1](./native-world-foundation-brief.md) defines the authenticated actor entrypoint, sequencing
submitter checks and narrow internal domain commands. The randomness module supplies recorded roots through that
entrypoint. The parity gate injects identical roots into today's derivation, preserving draw order, salts, timestamp
context, game scoping and increments. The foundation's five commits and immutable per-game presets remain unchanged.

For the later Bitcoin lottery, bind one root per game/phase after fixing the closed phase's contributor pool and before
publishing its root. Derive draws by phase/mine identity; claimant, batch composition/order and retry cannot affect
them. Owners and payout destinations still follow the frozen claim-time rules. The root binding uses the same durability
and failover guarantees and cannot be created as a fresh draw by a claim retry. See the
[frozen feature brief](./native-world-mines-bitcoin-villages-frozen-brief.md).

Slice and randomness tracks are measured separately. Report gates passed with reproducible artifacts. No claim of
unexploitable randomness, host-loss recovery or unchanged latency precedes the relevant implementation and tests.
