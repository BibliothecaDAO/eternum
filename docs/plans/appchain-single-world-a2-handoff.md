# A2 — Launch Pipeline Collapse — Codex Handoff

Status: **OPEN (2026-08-09).** Milestone: A2 of `docs/plans/appchain-single-world.md`. Prereq: A1 ACCEPTED (registrar
world on `feat/single-world-blitz`, 181/181 tests).

**Motto: KISS.** Every deliverable below is the smallest workable version. Do not add abstraction layers, config
frameworks, optional features, or refactors beyond what is listed. When two designs are close, pick the simpler one.
Overcomplication is a review finding, same as a bug.

## Mission

Today an appchain Blitz launch is: factory `create_game` ×~10 batched txs (~2.5 min) → poll `wf-WorldDeployed` →
~146-call config multicall → reserve-hyperstructures step → per-game role grant → torii indexer registration. Total ≈ 10
min. After A1 the world is persistent and `registrar.create_game` does everything per-game in ONE call (config copy,
hyperstructure ring reservation included). Collapse the pipeline so a UI-button launch reaches a joinable game in **< 30
s**, while the launch service Lambda and factory-v2 UI keep their exact contracts.

## The registrar API (already deployed logic — this is what the pipeline calls)

`contracts/game/src/systems/registrar/contracts.cairo:44-63`:

- `bootstrap_chain_config(chain_config: ChainConfig)` — once per world; caller must be the Dojo owner of
  `s2_blitz-registrar_systems` AND become the configured admin. Write-once.
- `register_preset(preset_config: PresetConfig, game_config: PresetGameConfig, side_tables: PresetSideTables)` —
  admin-only, write-once per `preset_id` (preset 0 reserved). `PresetSideTables` spans: weights, resource_factories,
  building_categories, structure_levels, hyperstructure_construction, resource_lists, resource_min_max_lists (all rows
  carry `preset_id`; the registrar stamps/validates it).
- `register_series(series_id, owner, num_games, total_chests, cap_ratio_bps)` — admin-only.
- `create_game(params: CreateGameParams) -> u32` — one tx per game. Params (contracts.cairo:20-41): name, preset_id,
  series_id + game_number_in_series (0/0 for standalone), start_settling_at, start_main_at, duration_seconds,
  end_grace_seconds, registration_grace_seconds, dev_mode_on, single_realm_mode, two_player_mode, registration_count_max
  (≤24), registration_start_at, fee_amount, biome_climate_config, use_map_override + map_override, seed (non-zero).
  Reserves the full hyperstructure ring inside this tx.
- The Cairo struct layouts are the calldata contract. The dispatcher test fixture
  (`contracts/game/src/systems/registrar/tests.cairo`, `dispatcher_lifecycle` mod) shows a complete working
  `register_preset` + `create_game` invocation — mirror it.

## Deliverables

**D1 — registrar call module** (`config/deployer/clean/registrar/` — one file if it fits): plain starknet.js
`Account.execute` wrappers for the four entrypoints above, ABI/address resolved from
`contracts/game/manifest_appchain.json` (same pattern as `deploy/appchain/scripts/*.ts`). No batching machinery, no
provider-package changes.

**D2 — preset builder**: a function mapping the EXISTING resolved config artifact
(`config/generated/blitz.appchain.json`, regenerated by `pnpm run config:sync:appchain` — keep this as the single source
of truth, invent no new format) → the `register_preset` calldata. The mapping mirrors what the 29 config steps
(`config/deployer/clean/config/steps.ts:110-147` + `native-steps.ts`) write today, re-bucketed per audit §3: static
rulebook members → `PresetConfig` + side tables; per-game members → `PresetGameConfig` template; chain addresses →
`ChainConfig`. Where a value is per-game (clock, fees, biome, map override, seed) it goes in `CreateGameParams` at
launch time, not the preset. CLI: `register-preset.ts --preset-id <n> [--dry-run]` (dry-run prints calldata + counts).

**D3 — world-deploy runbook script** (`deploy/appchain/scripts/deploy-s2-world.ts` + a short README section):
sequential, idempotent-where-possible steps the reviewer runs once per chain:

1. `sozo build && sozo migrate --profile appchain` (document the command; migration itself is run by the reviewer) —
   profile updated per D6.
2. Wire shared peripherals: set entry-NFT minter = `s2_blitz-blitz_realm_systems` address, loot-chest minter =
   `s2_blitz-prize_distribution_systems` address (reuse the grant-role call shapes from the existing grant
   workflows/scripts).
3. `bootstrap_chain_config` — addresses read from the same resolved config JSON (chain section) + env overrides; skip
   with a clear message if ChainConfig is already initialized.
4. `register-preset.ts --preset-id 1`; skip-if-registered.

**D4 — launch runner collapse** (`config/deployer/clean/launch/runner.ts` + `series-runner.ts`), appchain path only:

- `create-world` step → ONE `registrar.create_game` call built from the same launch inputs that feed the factory path
  today (`GAME_LAUNCH_*` env: name, start time, durationSeconds, devModeOn, twoPlayerMode, singleRealmMode,
  mapConfigOverrides, biomeClimateOverrides, blitzRegistrationOverrides). `version` maps to `preset_id` (the Lambda/UI
  keep sending `version` — parse it as the preset id, default 1). Record `createGameTxHash` in run-record artifacts plus
  ONE new artifacts key `gameId` (the block is extensible JSON; the UI ignores unknown keys). Delete the
  batching/submission-count/retry machinery from this path (single tx; keep one simple retry-on-timeout). Keep the
  account lease for this step only.
- `wait-for-factory-index` step (id unchanged, title "Waiting for game") → poll torii SQL for the
  `s2_blitz-GameRegistry` row with that game_id (2 s poll, 2 min timeout). This doubles as the indexing check.
- `configure-world`, `reserve-blitz-hyperstructures`, `grant-lootchest-role`, `create-indexer`, `sync-paymaster` → do
  not run and do not emit on the appchain path (run-record `steps[]` is data-driven; the UI renders what's present).
  Mainnet path emits exactly what it does today.
- Series (`create-series`) → one `register_series` call; per-game launches then pass series_id + game_number. Rotation
  logic sits on top unchanged.

**D5 — `game-launch.yml`**: gate the now-dead steps to `mainnet.*` environments (extend the existing
`endsWith(inputs.environment, '.blitz')`-style conditions); leave step order, run-record events, artifact upload, and
the lease helpers as they are. No new steps.

**D6 — appchain profile** (`contracts/game/dojo_appchain.toml`): namespace `default = "s2_blitz"`, new `[world] seed`
(`"s2_blitz_aws_1"`), writers list = the compiled `s2_blitz-*_systems` (mirror `dojo_local.toml`'s list post-A1, incl.
`registrar_systems`), `[env]` keeps rpc_url but account/key come from env (delete the hardcoded paymaster credentials).
`manifest_appchain.json` gets regenerated when the reviewer migrates — code against the manifest structure produced by
your local spike migration.

## What dies vs. survives (appchain path)

| `wf-WorldDeployed` torii poll (5 min budget)                 | `s2_blitz-GameRegistry` row poll (seconds)     |
| 29-step / ~146-call config multicall per game                | dies — preset registered once per chain        |
| reserve-blitz-hyperstructures step                           | dies — inside `create_game`                    |

## Facts that save time

- Workflow anatomy: single `launch` job, steps at `game-launch.yml:148-1010`; shell library generated at step "Prepare
  launch arguments" (:173-794); `run_launch_step` → `bun config/deployer/clean/cli/launch-step.ts --step <id>`;
  run-record events via `launch-run-store.ts`.
- Run store = GitHub branch `factory-runs`, written via Contents API (`config/deployer/clean/run-store/github.ts`); step
  ids in `config/deployer/clean/types.ts:16-25`; record schema `run-store/types.ts:196-217`. Keep ids/schema; emit a
  subset.
- Step registry comment (`config/deployer/clean/config/steps.ts:108-109`) calls itself "the contract between CI, the
  admin UI, and the onchain systems" — that contract is now scoped to mainnet.
- `config:sync:appchain` regenerates `config/generated/blitz.appchain.json` from `config/source/blitz/*`; the launcher
  loads it via `config-loader.ts:421-424`. Reuse; don't fork.
- Torii SQL base URL comes from `common/factory/endpoints.ts` / `TORII_URL` env (workflow :142).
- `sync-paymaster` is already a no-op on the appchain (embedded paymaster — `deploy/appchain/spike/README.md:154-162`).
- The Lambda (`deploy/appchain/cdk/lambda/launch-service/index.mjs`) dispatches with `ref: DEFAULT_WORKFLOW_REF` — it
  will point at this branch only when the reviewer flips it. You cannot break production from here.
- Local e2e: `deploy/appchain/spike/docker-compose.up` → migrate with a spike-rendered profile (see
  `spike/scripts/deploy-worlds.sh` for the render pattern) → run D3 → run the D4 create-game step via `launch-step.ts`
  pointed at localhost. Torii is optional locally (fork image); if you skip it, verify the GameRegistry row via a direct
  RPC `call` instead and note it.
