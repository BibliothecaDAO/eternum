## A. Cairo tuples have no agreed wire shape — boot fails on any game with a shareholder row

**Evidence.**

- Herald decodes model values with starknet.js `CallData.parse` (`apps/herald/src/model-registry.ts`, `decodeRecord`)
  and ships the result untouched. starknet.js (9.4.2 in Herald, 8.9.2 in the client) decodes a Cairo tuple as a **record
  with numeric keys**, not an array. Reproduced locally with the `Span<(ContractAddress, u16)>` ABI:
  `{"shareholders":[{"0":"0xa","1":"0x1388"}]}`.
- Live: `GET https://herald.realms.party/madara/games/21/snapshot?models=HyperstructureShareholders` (bltz-lilt-122)
  returns, verbatim:
  `"shareholders":[{"0":"0x615b21968063e60e2e8099da659e2d3ef9257c61356142b67a972978ddffc0f","1":"0x2710"}]`. Games 13
  and 20 have no shareholder row, so they boot.
- The client has **two** tuple readers and both demand an array:
  - `apps/game/src/sync/recs-game-sync-store.ts:132-144` `compileTupleSpanCoercer` —
    `Array.isArray(tuple) && tuple.length === memberCount` else throw. This is the boot failure; the throw propagates
    out of `applyBatch` and the recovery screen replaces the game.
  - `packages/core/src/utils/hyperstructure-shareholders.ts:26-30` `decodeShareholderTuple` — same check, same throw.
- Both readers also unwrap a `{ value: … }` envelope ("legacy typed-value envelope"). Nothing emits it any more; Herald
  is the only producer. Dead compatibility code.
- `recs-game-sync-store.parity.test.ts:57` pins an **invented** fixture (`[["0xa","0x1388"], { value: [...] }]`), so the
  suite is green while the live payload fails. A parity test that does not use the producer's shape is not a parity
  test.
- The class is wider than shareholders. Tuple spans in the sync manifest
  (`packages/types/src/dojo/contract-components.ts`): `HyperstructureShareholders.shareholders` (`Span<(u32, u16)>`,
  :899), `BattleEvent` (`Span<(u8, u128)>`, :3568), `ExplicitResourceBurn.resources` (:3710), `Transfer.resources`
  (:4007). Every one of them hits the same coercer. `ResourceArrival`'s 48 `slot_*` fields are tuple spans too, but the
  generated metadata labels them `"array"`, so the coercer cannot even tell (A.5 fixes the label; live evidence there).
- Third live instance: **u256 hand-mapped as `{ low, high }`.** starknet.js parses `u256` to one bigint, so Herald ships
  a single hex string; the generator says `RecsType.BigInt`. The hand file has `total_lords_pool: { low, high }` on
  `SeasonPrize` and the same shape wherever a u256 was hand-written (24 u256 members in the manifest). The captured
  parity fixture row `SeasonPrize {"total_lords_pool":"0x0"}` therefore fails today with "does not match its RECS struct
  schema" — the one red test in `apps/game` after the hygiene commit, and it is A.5's to fix by regeneration.
- Second instance, latent: a **bare** tuple. `LedgerRegistration.metadata` is `(felt252, felt252, felt252)`
  (`contracts/l3/game/src/models/ledger.cairo:25`), Herald-synced (`packages/core/src/sync/model-manifest.ts:98`), and
  hand-mapped in the generated file as `RecsType.BigIntArray` with the type string `"(felt252, felt252, felt252)"`
  (`contract-components.ts:912,920`). `tupleSpanMemberCount` matches only `^Span<\(`, so this field falls through to
  `compileArrayCoercer`, whose `requireGameSyncArray` throws on Herald's record. No live game has a ledger row yet
  (`?models=LedgerRegistration` is empty on games 13, 21, 22); the first registration through the ledger on a live world
  kills boot the same way. The generator does not know bare tuples at all: fed a manifest that contains this member it
  aborts with `No RECS mapping for member "metadata" of type "(core::felt252, core::felt252, core::felt252)"`.
- Truth drift, and it is the generator's. `contract-components.ts` is autogenerated; the source manifest is right
  (`contracts/l3/game/manifest_appchain_blitz.json:3154`, `Span::<(ContractAddress, u16)>`). The stale `(u32, u16)`
  survives because `packages/types/scripts/generate-contract-components.ts:235-253` splices the **baseline block** back
  in whenever the member names match, so a type change never reaches the output; and the tuple formatter at `:88`
  shortens only `core::integer::*` and `felt252`, so a fully qualified `ContractAddress` would be emitted long even on a
  fresh generate. The count matches so nothing throws today, but the metadata that drives the tuple coercer is wrong.
- **The generator's source manifest is stale, in the wrong direction.** `manifest_appchain_blitz.json` was last built on
  2026-08-31 (`adeb5419e5f`); Cairo moved on 2026-09-03 (`c2e8b487de6`). The committed manifest still carries
  `MMRConfig`, `BlitzEntryTokenRegister` and `entry_token_address` (0 hits in Cairo) and lacks
  `ledger_operator_address`, `player_registry_address` and `LedgerRegistration` (present in Cairo and hand-added to the
  generated file in `bbdd1d03224` / `b569e2aca6a`). Running the generator against HEAD today therefore produces a
  906-line diff (33 spliced, 79 generated, 6 carried) that **reverts** the generated file to the old schema. The fresh
  manifest is `manifest_madara.json`: listed in `contracts/l3/game/.gitignore` but tracked anyway, last committed
  2026-09-03 in `37b2c1e6c70` ("madara manifest after the ledger-decoupling world upgrade"), written by
  `deploy/madara-lab/scripts/deploy-world.sh` from the current Cairo, and the one Herald on the box loads via
  `HERALD_MANIFEST_PATH`. It has the ledger fields and no MMR, and it is the one that trips the bare-tuple abort above.
  Measured 2026-09-04; both runs restored, nothing staged. Latest commits checked (`ee29b2ef89f` back to `ce97c057df4`,
  and `origin/next` has nothing this branch lacks): no one has touched the generator, the appchain manifests, the
  coercer or the sign-out since.

**Class.** The shape of a Cairo tuple on the Herald wire is defined nowhere, so every consumer guesses, and the guesses
are tested against themselves.

**Fix — define the shape once, normalize once, at the ingest chokepoint.**

1. Write the rule in `apps/herald/src/stream-protocol.ts` (one comment where the payload types live): a Cairo tuple
   arrives as starknet.js emits it, a record keyed `"0".."n-1"`. Herald does not post-process decoded values; adding a
   type-directed walk there is more code than the client needs.
2. One reader, `cairoTupleMembers(value, memberCount): unknown[]` in `packages/core` (next to the sync helpers),
   accepting exactly that record shape and loud on anything else. The RECS coercer uses it and **stores the tuple as an
   array of members**. RECS is the one truth; downstream code reads arrays and knows nothing about the wire. The coercer
   selects it from the metadata type string for both forms, `Span<(…)>` (array of tuples) and bare `(…)` (one tuple);
   `tupleSpanMemberCount` becomes the one place that parses tuple types.
3. `decodeHyperstructureShares` reads the RECS array — no tuple-shape knowledge, no envelope unwrapping. Delete
   `unwrapValue` there and `unwrapTypedValue` in the store. If a `{ value }` producer still exists, name it in the PR;
   otherwise the envelope code goes.
4. Replace the parity fixture with the live payload above (game 21, verbatim, full address). Entity models are asserted
   through `getComponentValue` as today. `BattleEvent`, `ExplicitResourceBurn` and `Transfer` go through `applyEvent`
   (`recs-game-sync-store.ts:258-263`), which removes the row right after setting it, so the existing pattern cannot see
   them: subscribe to the component's `update$` stream around `applyEvent` and assert the tuple array on the emitted
   value. One test, three event rows. Add a `LedgerRegistration` row with `metadata: {"0":…,"1":…,"2":…}` to the entity
   half so the bare-tuple path is pinned before it fires live.
5. **The generator becomes the schema's only author.** Prerequisite commit, lands before the reader change. This
   replaces the earlier "reconcile seven blocks" instruction: measured on 2026-09-04, a pure generation from
   `manifest_madara.json` with no splicing differs from the committed file in 43 blocks, 20 of them substantive, plus 7
   blocks for models Cairo no longer has and 2 models the file lacks. Naming an allowed list is the wrong shape; the
   hand file is not a reference, it is nine months of drift. Decisions:
   - **Delete the splice.** `BASELINE_REF`, `assembleGroup`'s baseline branch, `spliceGameId`, `topLevelSchemaKeys` and
     the "carried" path all go. The generator is a pure function of `contracts/l3/game/manifest_madara.json` (the one
     manifest of a live world built from current Cairo; the appchain manifests cannot be rebuilt — no live world, RPC
     403 — and are deleted in section C); every block is generated every run. The 7 carried blocks (`Message`,
     `BlitzRealmPlayerRegister`, `BlitzRealmPositionRegister`, `BlitzRealmSettleFinish`, `MMRGameCommitted`,
     `CollectibleClaimed`, `SettleRealmData`) are not in Cairo and disappear; `tsc` names any consumer still reading
     them, and that consumer is dead too.
   - **Delete `customTypes`.** Zero consumers outside the generated file and its test. `metadata.types` stays: its one
     consumer is the tuple detection in the RECS coercer (`recs-game-sync-store.ts:152`), so it must be generated and
     exact, never hand-written.
   - **One type table, written in the generator as a table, not as special cases.** Herald's wire is fixed by
     `toJsonValue` (`apps/herald/src/model-registry.ts:190-205`): bigint → hex string, `Option` → value or `null`, unit
     enum → variant name, payload enum → `{ Variant: payload }`, struct → object, tuple → numeric-key record. Cairo →
     RECS follows from that; the mapping, Cairo → RECS schema → `types` label:
     - `bool` → `Boolean` → `bool`
     - `u8` `u16` `u32` → `Number` → the width
     - `u64` `u128` `u256` `felt252` `ContractAddress` `ClassHash` → `BigInt` → the name
     - unit enum (`Direction`, `ExploreFind`, `TroopType`…) → `String` → `enum`
     - payload enum (`Story`) → `T` → `enum`
     - `Option<X>` → the `Optional…` form of X's mapping → `Option<X>`
     - struct → nested schema, recursively → the leaf labels
     - `Span<primitive>` → `NumberArray` / `BigIntArray` → `Span<X>`
     - `Span<enum>` → `StringArray` → `Span<X>`
     - `Span<struct>` (`QuestLevels.levels`) → `T` → `Span<X>`
     - `Span<(…)>` and bare `(…)` → `NumberArray` / `BigIntArray` as the placeholder, the tuple reader (item 2) stores
       arrays → the full tuple string with short member names

     `ByteArray` keeps its existing `String` / `BytesArray` convention. No per-field exceptions: the `Stamina` u64 →
     BigInt carve-out goes, the hand file's `ContractAddress` → `String` choices (`Quest*.game_address`,
     `ExplorerMoveEvent` / `ExplorerRewardEvent.explorer_owner_address`) go, the 41 u64 → `Number` choices go.

   - **u64 is `BigInt`, everywhere, recursively.** The hand file maps 41 top-level u64 members to `Number` and 6 to
     `BigInt`, and the generator's `PRIMITIVE_RECS` says `Number`. Both are wrong for the type: Cairo uses u64 for
     fixed-point values — `TroopDamageConfig.damage_beta_small` is `0x4000000000000000` (2^62) in the captured parity
     fixture (`recs-game-sync-store.parity.json:494-495`, `contracts/l3/game/src/models/config.cairo:1123`) — so no
     `Number` mapping can hold, and a safe-integer guard would reject production data at boot. `BigInt` is exact; the
     width decides, not the field's meaning. Consumers that want a number say so at the read site (`Number(x)` for
     timestamps and ticks), which `tsc` enumerates. No guard, no fixed-point exception list.
   - **Regenerate. Every block. Then follow `tsc`.** The consumer breakage the type checker reports is the list of
     places the client disagreed with Cairo. Known today: `quest-utils.ts:20` compares `game_address` to the string
     `"0x0"` (becomes `0n`); `quest-entity-detail.tsx:64-70` and `resource-arrivals.ts:128-160` still read Torii's
     `{ value }` envelope (`level?.value?.time_limit?.value`, `resourceIdObj.value`), which Herald never sends — the
     arrivals panel has been decoding every slot to resource 0 / amount 0 since Herald replaced Torii. Rewrite both
     against the RECS array shape the tuple reader stores; there are 10 such envelope reads in `packages/core` +
     `apps/game`, all go in this commit (this is the deletion item 3 already asks for, finished).
   - **The test.** `packages/types` runs the generator against the committed manifest into a temp path and asserts it is
     byte-identical to the committed file. That single assertion covers stale manifest, hand edits and generator drift;
     it would have caught every item on this page. The Cairo model is the truth; Herald's `toJsonValue` is the wire; the
     generator is the client's reading of both. If a manifest member cannot be mapped by the table, the generator throws
     (it does today); no `"array"` placeholders, no `"?"` labels.

**Gate.** `packages/types` generator-is-a-no-op test green against the committed file, with no splice code left
(`grep -n "BASELINE_REF\|spliceGameId\|topLevelSchemaKeys\|customTypes" packages/types/scripts/generate-contract-components.ts`
returns nothing). Workspace `tsc` green. `pnpm test` in `apps/game` with the real fixtures green: entity rows for
`HyperstructureShareholders`, `LedgerRegistration` and `ResourceArrival` (live `slot_46` payload above), `update$`
assertions for the three tuple-span events, and one row each for the models whose schema changed (`QuestTile`,
`StructureVillageSlots`, `TileOpt`, `VillageTroop`, `StoryEvent`) captured from game 21 or the Herald history endpoint.
`pnpm exec vitest run` in `packages/core` green. Live: enter game 21 on `play.realms.party` — bootstrap completes, the
hyperstructure panel shows the shareholder at 100% (`0x2710` bp), the arrivals panel for the structure holding slot 46
lists two resources with real amounts, and a quest tile's level detail shows a time limit.

## B. Sign-out ends the identity session and leaves the wallet connected

**Evidence.**

- The only sign-out surface in the play client is `SignedInPanel.handleSignOut`
  (`apps/game/src/ui/modules/identity/landing-identity-chip.tsx:77-90`): `identityClient.signOut()` then
  `applySession(null)`. That ends the better-auth cookie session. Nothing else.
- The wallet connection is a second "logged in" fact and it survives: `useDisconnect` / `connector.disconnect()` has
  zero call sites in `apps/game/src`. `StarknetConfig` runs with `autoConnect`
  (`hooks/context/starknet-provider.tsx:57`), so starknet-react's `lastUsedConnector` re-attaches the same connector on
  every reload.
- Visible result (owner screenshots): after "Sign out" the popover shows a single "Sign in" button for the
  still-connected wallet (`identity-login.tsx:56`: `address ? "Sign in" : "Connect wallet"`). You cannot pick another
  wallet — which is the original report this sign-out was added for (`realms-client-brief.md:1988`, "can't log out to
  try another wallet").
- The `Unauthenticated / access denied` pair is the same fact seen from the other side. Our bundle has no gRPC client
  (`grep grpc apps/game/dist/assets/*.js` is empty); the only Go-style gRPC status in the stack is Cartridge's API
  behind the Controller keychain, which the provider file itself documents as "an authed gRPC client of its own".
  Re-attaching the Controller (autoConnect → `connect()` → keychain `probe`) with a dead Cartridge-side session yields
  that error through starknet-react's react-query hooks — twice, one per connect/probe call site. Not our server, but
  our reconnect. Verify with the network panel: the failing request host is `api.cartridge.gg`.
- Same class in the webapp, one layer deeper: `apps/realms/src/routes/profile.tsx:177` calls `identity.signOut` only,
  while `services/platform/wallet.ts:117` has a `disconnect` nobody wires to it. And that `disconnect` is not a
  disconnect: it nulls the in-memory account and the session ref but leaves `realms:last-wallet` (`wallet.ts:9`) in
  localStorage, and `ui/session.tsx:28` silently reconnects that wallet on every app start. Wiring it as-is would fix
  the click and not the reload.
- What is already right: `GameplayAccountSync` derives the gameplay account from the session and resets it on status
  change (`gameplay-account-sync.tsx:60`). No fix needed there.

**Class.** "Signed in" is two facts in two owners (identity session, wallet connection) and sign-out ends one of them.
Every surface that has to be re-taught this is a future instance.

**Fix — one sign-out that ends both, per app, at the one surface each app has.**

1. Play client: `handleSignOut` = `identityClient.signOut()` → `disconnectAsync()` (starknet-react; it calls
   `connector.disconnect()` and clears `lastUsedConnector`) → `applySession(null)` → close the popover. Order matters:
   the session is the fact, the wallet is the credential that minted it. Failure behaviour, in that order:
   - identity sign-out throws → nothing changes: session kept, wallet kept, error shown in the panel's existing `error`
     slot (the panel is still mounted because the session is still there).
   - identity sign-out succeeded and `disconnect` throws → the session is gone server-side, so clear it and close the
     popover anyway; `applySession(null)` unmounts `SignedInPanel` (`landing-identity-chip.tsx:64`), so the local error
     slot cannot show it. Report through the existing `console.error("identity_sign_out_failed", …)` line. No toast, no
     new channel: a wallet that failed to detach after a successful sign-out is a next-reload nuisance, not a blocker.
2. Webapp: `wallet.disconnect` becomes a real disconnect — it also removes `realms:last-wallet`, so `session.tsx`'s
   silent reconnect has nothing to reconnect. Same operation, one more line; no separate `forgetWallet`. Then
   `profile.tsx` sign-out runs `identity.signOut` then `wallet.disconnect`, with the same failure order as the client.
3. No new state, flag, or store. Nothing new is exported. If either app grows a second sign-out surface, that is the bug
   to refuse in review.
4. `apps/game/AGENTS.md` requires a `latest-features.ts` entry for a player-visible change: one `fix` entry, "Sign out
   now disconnects the wallet so you can sign in with another one."

**Gate.** Chip test: sign-out calls `signOut`, then the connector `disconnect`, then the session is null and the popover
closed; a failing `signOut` leaves session and wallet untouched with the error visible; a failing `disconnect` after a
successful `signOut` still leaves the session null. Webapp tests (`pnpm --dir apps/realms test`): `disconnect` removes
`realms:last-wallet` and a following `reconnect` yields no session; profile sign-out calls both. Live: sign out on
`play.realms.party`, the popover closes; reopen it — it shows the connector list (Controller / Ready / Braavos), not
"Sign in"; reload — chip is "Sign in" with no autoConnect probe and no `Unauthenticated` line in the console;
`app.realms.party` profile shows signed out after the same flow and stays signed out across a reload.

**Non-goal.** The Cartridge-side `access denied` itself. Controller is an identity wallet option on borrowed time
(Cartridge EOL); if its probe keeps failing for signed-out users after B lands, the answer is to drop the connector, not
to retry around it.

## C. The `appchain` chain is dead — delete it, not just its manifests

**Owner decision (2026-09-04):** delete the appchain manifests and profiles. Taken here to its class.

**Evidence.**

- `GAME_CHAIN_NAMES` (`packages/chain/chain-guard.js:8-11`) has exactly two chains: `appchain` (`WP_REALMS_DEV`) and
  `madara`. `appchain` is the AWS-hosted dev appchain at `http://52.54.98.119`; it answers 403 and is being switched
  off. The shared env list (`config/shared/game-environments.ts`) already carries `madara.blitz` alone.
- Everything under the `appchain` id is therefore unreachable configuration: two game profiles + two manifests
  (`contracts/l3/game/dojo_appchain_blitz.toml`, `dojo_appchain_eternum.toml`, plus the hyphenated duplicates
  `dojo_appchain-blitz.toml`, `dojo_appchain-eternum.toml`, `manifest_appchain_blitz.json`,
  `manifest_appchain_eternum.json`), the Scarb profile sections (`contracts/l3/game/Scarb.toml:62-65`,
  `contracts/l3/factory/Scarb.toml:28-29`), the factory profile and manifest (`contracts/l3/factory/dojo_appchain.toml`,
  `manifest_appchain.json`), `contracts/common/.env.appchain`, `contracts/common/addresses/appchain.json`, the generated
  balance configs (`config/generated/blitz.appchain.json`, `eternum.appchain.json`), the client hooks that only exist
  for it (`apps/game/src/hooks/appchain-faucet-account.ts`, `appchain-worlds-summary.ts`), the `copy-abis` targets
  (`scripts/copy-abis.mjs:21`), and the root / `config` package scripts (`config:sync:appchain*`,
  `manifest:copy-abis:appchain:*`, `config/package.json:6-8`).
- The chain id itself is a literal in 65 files (22 non-test), among them `apps/game/env.ts:54` (`VITE_PUBLIC_CHAIN` enum
  and the master-credential rule at `:176-186`), `contracts/utils/utils.ts:155` (`getGameManifest`),
  `config/utils/utils.ts:22-25`, `config/source/{blitz,eternum}/chains.ts`, `common/factory/endpoints.ts`,
  `packages/client/src/config.ts`, `apps/operator/src/{server,writers}.ts`, and the CI job that runs the client suite
  with `VITE_PUBLIC_CHAIN: "appchain"` (`.github/workflows/test-client.yml:59`).
- Earlier briefs deferred this ("appchain retires on its own schedule",
  `madara-lab-game-launch-scheduler-codex-brief.md:112`). The rotation and prune workflows they said to fold in at
  retirement are already gone from `.github/workflows`. Nothing is left to migrate; only to delete.

**Class.** A chain id that has no RPC, no manifest and no deployment is a silent default waiting to be selected.
Deleting the files while keeping the id would leave `getGameManifest("appchain")` and `VITE_PUBLIC_CHAIN=appchain` as
loud-at-runtime dead ends: wired-or-deleted says delete.

**Fix — remove `appchain` from `GAME_CHAIN_NAMES` and let the type checker enumerate the rest.**

1. Delete `appchain` from `CHAIN_NAMES` / `GAME_CHAIN_NAMES` in `packages/chain/chain-guard.js` and `.d.ts`. `madara` is
   the only chain until the mainnet appchain is added by its own brief.
2. Delete every file in the evidence list above. Remove the two Scarb profile sections, the `copy-abis` targets, and the
   root / `config` scripts.
3. Follow `tsc` across the workspace: every `case "appchain"` / `chain !== "appchain"` branch goes, along with the
   variables that only fed it (the faucet credentials in `apps/game/env.ts`, `resolveAppchainToriiBaseUrl`, the
   `appchain` keys in `config/utils/utils.ts`). Where a branch was the only non-madara path, the switch collapses to a
   direct call; do not leave a one-armed switch. `getGameManifest` keeps its chain parameter only if a second chain
   still calls it; otherwise it becomes `loadMadaraGameManifest` and the parameter goes.
4. Tests: change the chain literal to `madara` where the test is about behaviour, delete the test where it was about the
   appchain itself (`appchain-faucet-account.test.ts`, the "default appchain chain" cases in
   `run-renderer-scene-smoke.test.mjs`). `game-scope.test.ts:20` reads `manifest_madara.json`. `test-client.yml:59` sets
   `VITE_PUBLIC_CHAIN: "madara"` and drops the master-credential placeholders that only the appchain rule required.
5. Nothing new: no `legacy` flag, no compatibility alias, no `// removed` comments.

**Gate.** `pnpm exec tsc -b` (or the workspace typecheck) green with zero remaining `"appchain"` literals outside
`docs/`:
`grep -rn '"appchain"' --include=*.ts --include=*.tsx --include=*.mjs --include=*.yml . | grep -v node_modules | grep -v docs/`
returns nothing. `pnpm test` in `apps/game`, `pnpm exec vitest run` in `packages/core` and `config`, `pnpm run knip`
(expect it to flag nothing new and to stop flagging whatever the appchain files kept alive). `scarb build` in
